# 02 · 系统架构（修订版）

> 在 OpenAI 原架构基础上做了两处关键调整：(1) Foundation Model 从核心层移到"挑战者"槽位（默认不在 v1 关键路径）；
> (2) 在数据层和模型层之间显式插入 **回测/评估骨架** 作为一等公民——因为评估是信任的来源，不是事后 notebook。

---

## 1. 分层架构

```text
┌────────────────────────────────────────────────────────────┐
│ 数据导入层  (CSV/Excel 上传 → 校验)                          │
├────────────────────────────────────────────────────────────┤
│ 销售语义数据层  (fact_* / dim_* 标准表, 见 03-data-contract) │
├────────────────────────────────────────────────────────────┤
│ 数据质量门禁  (validate: 唯一键/缺失/突变/口径一致性)         │
├────────────────────────────────────────────────────────────┤
│ 特征工程层  (lag / rolling / 价格促销 / 库存 / 生命周期 / 层级)│
├────────────────────────────────────────────────────────────┤
│ 模型层                                                       │
│   ├─ Baseline      : SeasonalNaive / AutoETS / AutoARIMA     │
│   ├─ 主预测器       : LightGBM Quantile (v1 主力)            │
│   ├─ 备选树模型     : CatBoost Quantile                      │
│   ├─ 新品          : Analog Launch Model                     │
│   └─ [挑战者/后期]  : TimesFM / Chronos-2  (Phase 4, 默认关) │
├────────────────────────────────────────────────────────────┤
│ Model Router + Ensemble  (权重由 rolling backtest 学出)      │
├────────────────────────────────────────────────────────────┤
│ 层级预测校准  (HierarchicalForecast: 保证各级数字一致)        │
├────────────────────────────────────────────────────────────┤
│ ★ 回测 / 评估骨架 (rolling backtest, FVA, 指标) — 一等公民 ★  │
├────────────────────────────────────────────────────────────┤
│ 业务决策层                                                   │
│   ├─ sell-out 预测                                           │
│   ├─ sell-in 建议  (库存约束)                                │
│   ├─ 库存风险  (缺货 / 压货)                                 │
│   ├─ 促销场景模拟  (相关性, 带护栏)                          │
│   └─ 新品铺货建议                                            │
├────────────────────────────────────────────────────────────┤
│ override / 审计层  (谁改了什么, 为什么)                       │
├────────────────────────────────────────────────────────────┤
│ Dashboard (Streamlit 起步)  +  Agent 解释层 (只解释不决策)    │
└────────────────────────────────────────────────────────────┘
```

### 与原架构的差异说明

- **回测/评估骨架被提升为显式分层**：它位于模型层与业务层之间，所有模型/ensemble 在进入业务决策前都必须先通过它产出 FVA 与误差画像。信任来自这一层。
- **Foundation Model 标注为 `[挑战者/后期]` 且默认关闭**：v1 不依赖它跑通闭环，理由见 `04` 与 `REVIEW`。
- **override/审计被显式画成一层**：它不是 Dashboard 的附属功能，而是贯穿系统的信任机制。

## 2. 数据流（一次预测运行 forecast_run 的生命周期）

```text
上传原始数据
  → 写入语义层 (fact_*/dim_*)
  → 质量门禁 (不过则中止并报告)
  → 构建特征 (严格按 as-of 时点, 防泄漏)
  → 各模型分别产出 P10/P50/P90
  → Model Router 按近期回测表现加权 ensemble
  → 层级校准 (reconcile, 使各级一致)
  → 写入 forecast_output (带 forecast_run_id)
  → 业务层计算 sell-in 建议 / 风险 / 场景
  → 人工 review, 可 override (写 forecast_override)
  → Agent 基于结构化事实生成解释/周报
  → Dashboard 呈现
```

> **关键纪律**：特征构建必须严格"as-of"——只能用预测时点之前可见的信息。
> 任何"未来才知道"的字段（除显式声明的 known future covariate）都不得进入特征。详见 `04`。

## 3. 技术选型（与原方案一致，仅调整优先级）

| 层 | 选型 | v1 是否关键路径 |
| --- | --- | --- |
| 数据处理 | pandas / polars / DuckDB | ✅ |
| 存储 | 起步 DuckDB（单文件、零运维），扩展再上 Postgres | ✅ |
| 主预测框架 | MLForecast（多序列 + 外生变量 + lag/rolling） | ✅ |
| 统计 Baseline | StatsForecast（AutoETS / AutoARIMA / SeasonalNaive） | ✅ |
| 主模型 | LightGBM Quantile（价格/促销/库存/渠道特征最适合树模型） | ✅ |
| 备选树模型 | CatBoost Quantile | ⬜ 可选 |
| 层级校准 | HierarchicalForecast（BottomUp/TopDown/MinTrace 等） | ✅ |
| Foundation Model | TimesFM + Chronos-2 | ⛔ Phase 4 挑战者 |
| 神经模型 | NeuralForecast | ⛔ 第二阶段 |
| 自动 benchmark | AutoGluon-TimeSeries | ⬜ 评估期可选 |
| Dashboard | Streamlit 起步，验证闭环后再考虑 Next.js | ✅ |
| Agent | LLM + 规则 + 结构化结果（只解释） | ✅（薄层） |

> 选型本身和原方案基本一致——本项目的差异不在"用什么库"，而在**优先级与边界**：
> 先用成熟、可解释、可本地跑的组件把信任闭环跑通，再引入 Foundation Model 等重型组件。

## 4. 部署形态（v1）

- **单机 / 单容器即可**：DuckDB 单文件 + Streamlit 进程，无需 GPU。
- **批处理节奏**：每周一次 forecast_run（可手动触发），不追求实时。
- **可复现**：每次 run 带 `forecast_run_id`、输入数据快照、模型版本、随机种子，保证回测可复现。
- 选择不依赖 GPU/Foundation Model 的形态，是为了让 v1 能在最简单的环境里被反复演示给高层看——演示环境越简单，越不容易出"现场翻车"事故。
