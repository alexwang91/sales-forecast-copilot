# 05 · 业务决策逻辑

> 这是系统真正的价值所在——把"预测"变成"行动"。沿用原方案的 sell-out → sell-in 思路（正确且关键），
> 补充三件事：**库存规则的口径、促销模拟的诚实边界、新品 Analog 的可解释性。**

---

## 1. 核心原则：不要直接预测 sell-in

```text
Step 1  预测真实需求 sell-out          (模型层)
Step 2  结合库存算 sell-in need         (库存约束)
Step 3  结合渠道策略给 sell-in 建议     (规则)
```

基础公式：
```text
suggested_sell_in =
    forecast_sell_out_next_4w
  + target_ending_inventory
  − current_channel_inventory
```

> 前提：sell-out 数据可得（见 `03 §1`）。若处于情形 C（仅 sell-in），本模块需降级，
> 并在 UI 显式标注"基于出货预测的补货参考，非需求驱动"。

---

## 2. 库存/补货规则（分位数 → 行动）

不同库存态势用不同分位数，把风险偏好显式化：

| 情况 | 规则 |
| --- | --- |
| 缺货风险高 | 用 **P75 / P90** 需求（宁可多备） |
| 库存过高 | 用 **P40 / P50** 需求（克制补货） |
| 新品上市 | 用 launch allocation rule（见 §4） |
| EOL 阶段 | 限制补货，避免尾货积压 |
| 强促销前 | 促销前提前补库存（结合 future_promo） |
| 渠道周转慢 | 降低建议发货 |

派生风险指标：
```text
weeks_of_cover    = channel_inventory / 近期周均 sell-out
stockout_risk     = P(未来需求 > 可用库存)        // 由分位数预测推出
overstock_risk    = f(weeks_of_cover 超目标的程度)
```

系统据此回答：未来 4 周卖多少 / 库存够不够 / 这周补多少 / 补多了会不会压货 / 促销前要不要加货。

> 设计纪律：每个建议数字旁边都给出**它依据的分位数和库存假设**，让使用者能判断"系统为什么这么建议"。

## 3. 促销模拟器：诚实边界（与原方案的措辞分歧）

> 原方案把它列为 Non-Goal（不做严肃因果 uplift）是对的，但 Promotion Simulator 页面**容易让人误以为是因果 what-if**。
> v1 必须显式声明它的性质，否则一次"模拟说会涨 20% 结果没涨"就会击穿信任。

**v1 促销模拟器的定位：相关性场景探索 + 规则护栏，不是因果 uplift 模型。**

- 它基于历史"在相似折扣/促销类型下观察到的 sell-out 模式"给出**情景区间**（P10/P50/P90），不是"如果做这个促销，因果上会多卖 X"。
- 每个场景输出都带**不确定性区间**和**类比样本量**（基于多少个历史相似促销得出，样本太少要标注"低置信"）。
- UI 文案明确："以下为基于历史相似促销的情景参考，非因果保证。"
- 场景维度：无促销 / 10% / 15% / 20% 折扣 / bundle / operator campaign。
- 输出：预计 sell-out（P10/P50/P90）、库存消化、缺货风险、建议补货量。

> 因果 uplift（控制混杂、反事实）是后期增强项，不在 v1。**v1 宁可少承诺，不可过度承诺。**

---

## 4. 新品 Launch：独立的 Analog 模型

新品没有历史销量，时间序列/树模型无从学起。用类比（analog）而非让模型"猜"：

```text
New SKU Forecast =
    相似老品 launch curve
  × 国家修正
  × 渠道修正
  × 价格带修正
  × 促销修正
  × 首批库存约束
```

相似 SKU 匹配维度：
```text
category, series, price_tier,
predecessor_sku, launch_month,
country, channel_type,
initial_inventory, promotion_flag
```

输出：首 4 周各周 P10/P50/P90 + 首批铺货建议。

**v1 做法（刻意简单且可解释）**：
- 只做"找 3–5 个相似旧品、生成 launch curve、做上述修正"。
- **可解释性是卖点**：UI 要展示"用了哪几个类比 SKU、为什么相似、各自 launch 曲线"，让产品经理能认同或否决类比选择。
- 这比让 Foundation Model 猜一个无历史的新品**可信得多**——可信度本身就是这里选 analog 而非 ML 的理由。

---

## 5. 业务层与模型层的边界

- 模型层只负责"需求会是多少"（sell-out 的概率分布）。
- 业务层负责"那我们该怎么做"（sell-in、补货、促销、铺货）——这一层是**规则 + 库存约束**，透明、可被业务质疑和调整。
- 这样分离的好处：模型可以替换/升级，而业务规则保持稳定、可被销售和供应链理解——**让业务规则透明，是让业务侧愿意采用的前提。**
